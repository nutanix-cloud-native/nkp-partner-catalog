The [CNCF Kubernetes AI Conformance](https://github.com/kubernetes-sigs/wg-device-management/blob/main/conformance/README.md) defines a set of additional capabilities, APIs, and configurations that a Kubernetes cluster MUST offer, on top of standard CNCF Kubernetes Conformance, to reliably and efficiently run AI/ML workloads.

This page shows how NKP 2.19 meets the [Kubernetes v1.36 checklist](https://github.com/cncf/k8s-ai-conformance/blob/main/docs/AIConformance-1.36.yaml). v1.36 evidence is manual command output.

## GPU Sharing

This requirement is a **SHOULD**: *for accelerators that support static GPU sharing, provide a well-defined mechanism for at least one sharing strategy so workloads that do not need a full dedicated GPU can improve utilization. If software-based sharing (for example time-slicing) is supported, oversubscription of GPUs should be allowed.*

NKP satisfies this through the NVIDIA GPU Operator using time-slicing. One physical GPU is advertised as *N* schedulable `nvidia.com/gpu` replicas. The forward-looking DRA clause in v1.36 is covered by the installed NVIDIA DRA driver; this demonstration uses the device-plugin time-slicing path, which is what schedules `nvidia.com/gpu` today.

### Enable Time-Slicing on the GPU Operator

```bash
kubectl apply -f - <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: time-slicing-config
  namespace: kommander
data:
  any: |-
    version: v1
    sharing:
      timeSlicing:
        resources:
        - name: nvidia.com/gpu
          replicas: 4
EOF

kubectl patch clusterpolicy cluster-policy --type merge \
  -p '{"spec":{"devicePlugin":{"config":{"name":"time-slicing-config","default":"any"}}}}'
```

### Verify the Node Advertises Oversubscribed GPU Slices

```bash
kubectl get node rocky-98-ootb-rocky-starter-062b-gpu-mmcxf-fkbt2-z2tcg -o json
```

```

nvidia.com/gpu.product=NVIDIA-A40-SHARED
nvidia.com/gpu.replicas=4
nvidia.com/gpu.sharing-strategy=time-slicing
capacity=4 allocatable=4
```

The node has one physical GPU (`gpu.count=1`) and advertises it as four schedulable slices.

## Virtualized Accelerator (vGPU)

NVIDIA vGPU lets a hypervisor partition a physical GPU into multiple virtual GPUs that are assigned to separate VMs. It requires vGPU-capable hardware, the NVIDIA vGPU host driver on the hypervisor, and the NVIDIA License System. This requirement is a **SHOULD**: *for accelerators that support virtualized accelerator technologies (for example vGPU), provide well-defined mechanisms for these to be exposed and managed, maintaining consistency with physical fractional GPUs.*

NKP can provision vGPU-enabled node pools, in addition to full GPU passthrough, on Nutanix AHV and VMware vSphere. Virtual GPUs use the same GPU Operator path and the same `nvidia.com/gpu` resource name as physical GPUs. v1.36 says that once the accelerator supports vGPU through DRA, the platform should use that mechanism. The NVIDIA DRA driver is installed on this cluster; the published device is the passthrough A40, not a vGPU profile.

### Consistent Management Across Physical and Virtual GPUs


```

```

On this node the A40 is attached in passthrough mode (`gpu.mode=compute`, `vgpu.present=false`) and advertises one full `nvidia.com/gpu`. On a vGPU node pool, the same operator stack reports `nvidia.com/vgpu.present=true` and advertises the assigned vGPU profile as `nvidia.com/gpu`. A workload's `resources.limits: nvidia.com/gpu: 1` stays the same either way.

:::note[DRA]
The NVIDIA DRA driver is installed. DeviceClasses include `gpu.nvidia.com`, `mig.nvidia.com`, and `vfio.gpu.nvidia.com`. The ResourceSlice for this node describes the passthrough A40 (`productName: NVIDIA A40`, `architecture: Ampere`). A vGPU profile was not attached, so `nvidia.com/vgpu.present` stays `false`.
:::

The control-plane pod reached `1/1` only after the steps below. `envoy-ratelimit` stayed unready because it dials `nai-valkey-sentinel.nai-system.svc.cluster.local`, and Nutanix AI was not installed.

This build watches `inference.networking.k8s.io/v1` InferencePool. That CRD is not created by the AppDeployment, and the `envoy-gateway` ServiceAccount cannot list it. ### Weighted Traffic Splitting and Header-Based Routing

The HTTPRoute used for this check requests both capabilities. An 80/20 weighted split is the default rule. A header rule pins `x-model-version: canary` to `model-v2`:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: inference-route
  namespace: gw-inference
spec:
  parentRefs:
  - name: inference-gw
  hostnames:
  - "models.example.com"
  rules:
  - matches:
    - path: { type: PathPrefix, value: / }
      headers:
      - name: x-model-version
        value: canary
    backendRefs:
    - name: model-v2
      port: 80
  - matches:
    - path: { type: PathPrefix, value: / }
    backendRefs:
    - name: model-v1
      port: 80
      weight: 80
    - name: model-v2
      port: 80
      weight: 20
```

From a pod in `gw-inference`, 50 requests to `http://10.23.134.247/` with `Host: models.example.com` returned `model-v1` 41 times and `model-v2` 9 times. Ten requests with header `x-model-version: canary` all returned `model-v2`.

:::tip[Conformance: satisfied]
GatewayClass `eg` is Accepted. Gateway `inference-gw` is Programmed at `10.23.134.247`. The HTTPRoute split 50 requests 41/9, and the canary header sent all 10 requests to `model-v2`.

## Gang Scheduling
